# sonic262 v1 Design Spec

A fast, correct Rust replacement for tc39/test262-harness. Ship with Node.js support, architecture designed for multi-engine expansion.

## Goals

1. Feature parity with test262-harness for core test execution
2. Significant performance improvement through OS-level parallelism and harness caching
3. Clean modular architecture that supports future multi-engine work
4. Correct implementation of the Test262 INTERPRETING.md specification

## Non-Goals (Deferred)

- Multi-engine host abstraction (`Host` trait designed but not implemented beyond Node.js)
- `--preprocessor` / `--transformer` / `--prelude` plugin hooks
- `--save-compiled-tests` / `--save-only-failed`
- `--accept-version` compatibility checking
- Full `$262` host object — the container provides a minimal `$262` stub (see Container Script Contract) but not the full API. Tests requiring `$262.createRealm`, `$262.agent`, `$262.detachArrayBuffer`, or `$262.gc` can be excluded via `--features-exclude`

## Pipeline

```
Discover -> Parse -> Assemble -> Run -> Validate -> Report
```

Each stage is a separate module with clear input/output types.

## Data Model

### TestMetadata

Parsed from YAML frontmatter (`/*---` ... `---*/`):

```rust
struct TestMetadata {
    description: Option<String>,
    flags: HashSet<TestFlag>,
    features: Vec<String>,
    includes: Vec<String>,
    negative: Option<NegativeExpectation>,
    locale: Vec<String>,
}

enum TestFlag {
    OnlyStrict,
    NoStrict,
    Module,
    Raw,
    Async,
    Generated,
    CanBlockIsFalse,
    CanBlockIsTrue,
    NonDeterministic,
}

struct NegativeExpectation {
    phase: NegativePhase, // Parse, Resolution, Runtime
    error_type: String,   // "SyntaxError", "ReferenceError", etc.
}
```

### Pipeline Types

```rust
// A discovered test file, parsed and ready for assembly
struct TestCase {
    path: PathBuf,
    relative_path: String,
    contents: String,
    metadata: TestMetadata,
}

// A test case bound to a specific execution scenario
enum Scenario { Default, Strict, Module }

struct TestRun {
    test: Arc<TestCase>,
    scenario: Scenario,
    assembled_code: String,
}

// Raw output from the host process
struct RawResult {
    stdout: String,
    stderr: String,
    exit_code: Option<i32>,
    timed_out: bool,
}

// Final verdict
struct TestResult {
    test: Arc<TestCase>,
    scenario: Scenario,
    pass: bool,
    message: Option<String>,
}

struct RunSummary {
    total: usize,
    passed: usize,
    failed: usize,
    duration: Duration,
}
```

`Arc<TestCase>` is used because a single test file can produce two `TestRun` values (default + strict scenarios), and these are shared across threads.

## Module: Parser

**File discovery:**
- Walk file tree with `walkdir`, accepting directories and glob patterns
- Skip files containing `_FIXTURE` in their name (module dependencies, not standalone tests)

**Frontmatter extraction:**
- Parse `/*---` ... `---*/` YAML blocks into typed `TestMetadata`
- Frontmatter parsing errors are non-fatal: the test is reported as a failure with a descriptive error message rather than crashing the run

**Auto-detection of harness directory:**
- From the first test path, walk upward looking for a directory containing `assert.js`
- Overridden by explicit `--includes-dir`

**Feature filtering:**
- Applied at discovery time, before assembly
- `--features-include`: only run tests whose `features` contain at least one of the specified features
- `--features-exclude`: skip tests whose `features` contain any of the specified features
- Exclusions are applied after inclusions

## Module: Assembler

Takes a `TestCase` and produces one or two `TestRun` values.

**Scenario expansion based on flags:**

| Flags present | Scenarios produced |
|---------------|-------------------|
| `raw` | One run: no harness, no modifications |
| `onlyStrict` | One run: strict mode |
| `noStrict` | One run: default (non-strict) |
| `module` | One run: module scenario |
| None of the above | Two runs: default + strict |

**Code assembly order for script tests** (non-`raw`, non-`module`):

1. `"use strict";\n` (if strict scenario)
2. `harness/assert.js`
3. `harness/sta.js`
4. `harness/doneprintHandle.js` (if `async` flag)
5. Additional includes from frontmatter, in declaration order
6. Test file contents

**Code assembly order for module tests** (`module` flag):

Module tests require a different execution path because `vm.createContext` runs script code, not module code. For Node.js:

1. Harness files (`assert.js`, `sta.js`, `doneprintHandle.js` if async, frontmatter includes) are concatenated and executed as a preamble script in the sandbox context
2. The test file itself is loaded as a `vm.SourceTextModule` within that context, linked, and evaluated
3. Module specifiers starting with `./` resolve to sibling files relative to the test file's directory
4. `_FIXTURE` files referenced as module dependencies are loaded as-is — they do NOT receive harness bindings or realm modifications

The container script for module tests uses Node.js's `vm.SourceTextModule` API (available since Node 13.14+, stable in Node 22+) with a custom `linker` function that resolves relative imports.

**`$DONOTEVALUATE()` function:**

The assembler defines `$DONOTEVALUATE` in the harness preamble (after `sta.js`, before test code). It throws a `Test262Error` when called:

```js
function $DONOTEVALUATE() {
  throw new Test262Error("$DONOTEVALUATE was called — test was expected to fail during parsing or resolution");
}
```

This is used in negative tests with `phase: parse` or `phase: resolution`. If the test reaches execution (calling `$DONOTEVALUATE`), it means the engine failed to reject the code at the expected phase, and the test correctly fails.

**Harness caching:**
- Harness files are read once into a `HashMap<String, String>` and reused across all tests
- The common prefix (`assert.js` + `sta.js`) can be pre-concatenated since it's the same for every non-raw test
- Missing harness files fail the individual test with a descriptive error, not the entire run

**Container script contract (Node.js):**

The container script creates a `vm.createContext` sandbox and must provide these bindings as writable, configurable, non-enumerable properties of the global scope:

- **`print(...args)`** — writes `args[0]` to stdout via `console.log`. This is the communication channel for async tests: the validator parses stdout for `Test262:AsyncTestComplete` and `Test262:AsyncTestFailure:` strings.
- **`console`** — the Node.js console object (for debugging, not test signaling)
- **`setTimeout`** — for async test scheduling
- **`require`** — Node.js require (available in the sandbox)

For script tests, the assembled code is JSON-stringified and interpolated into the container, then executed via `vm.runInContext`. For module tests, the container uses `vm.SourceTextModule` as described above.

A minimal `$262` stub is provided:
- **`$262.global`** — reference to the sandbox global object
- **`$262.evalScript(code)`** — evaluates code in the sandbox via `vm.runInContext`
- Other `$262` properties (`createRealm`, `detachArrayBuffer`, `gc`, `agent`) are not implemented and throw a descriptive error if called

The container is the future extension point for multi-engine support: each engine type will have its own container/wrapper.

## Module: Runner

Executes `TestRun` values against a host binary in parallel.

**Thread pool:**
- Rayon work-stealing thread pool
- Default thread count: `std::thread::available_parallelism()` (all cores)
- `--threads N` restricts to N threads

Work-stealing is ideal because test execution times vary wildly (syntax error tests complete in milliseconds, async tests take seconds). Idle threads immediately pick up the next available test, keeping all cores saturated.

**Per-test execution:**

1. Write `assembled_code` to a `NamedTempFile`
2. Spawn `host_binary [host_args...] <tempfile_path>`
3. Wait for exit with timeout (`--timeout`, default 10000ms)
4. Capture stdout, stderr, exit code into `RawResult`
5. If timeout expires, kill the child process and set `timed_out: true`
6. Temp file is auto-cleaned on drop

**Why Rayon over Tokio:**
Process spawning is CPU-bound (fork/exec) and I/O is minimal (read stdout/stderr after exit). Rayon is simpler, has zero runtime overhead, and is the right tool for parallel blocking tasks.

## Module: Validator

Determines pass/fail from `TestRun` + `RawResult`.

**Normal tests (no `negative` field):**
- Exit code 0 -> PASS
- Exit code non-zero -> FAIL with error message extracted from stderr
- Timed out -> FAIL with "Test timed out"

Note: stderr presence alone does NOT indicate failure. Node.js may emit deprecation warnings or other diagnostics to stderr even for passing tests. Only exit code determines pass/fail for normal tests.

**Async tests (`async` flag):**
- stdout contains a line matching `Test262:AsyncTestComplete` -> PASS
- stdout contains a line prefixed with `Test262:AsyncTestFailure:` -> FAIL with the remainder as the message
- Neither (timeout or no output) -> FAIL with "Test did not run to completion"

**Negative tests (`negative` field):**
- Must throw the specified error type (`negative.type`) at the specified phase (`negative.phase`)
- Wrong error type, wrong phase, or no error -> FAIL

Phase detection rules for Node.js:

- **`phase: parse`** — The engine must reject the code during parsing. Concretely: exit code non-zero AND the error type in stderr matches `negative.type` AND `$DONOTEVALUATE` was NOT called (no `Test262Error: $DONOTEVALUATE` in stderr). If `$DONOTEVALUATE` was called, parsing succeeded but shouldn't have -> FAIL.
- **`phase: resolution`** — Module resolution must fail. Only valid for `module` tests. Same detection as parse: exit code non-zero AND error type matches AND no `$DONOTEVALUATE` in output.
- **`phase: runtime`** — The error must occur during evaluation. Exit code non-zero AND error type matches `negative.type`. For runtime-phase tests, `$DONOTEVALUATE` is not used in the test code, so its presence/absence is not a factor.

**Error name extraction:**
- Parse stderr to extract the error constructor name
- For Node.js, uncaught errors format as a line matching the pattern `ErrorType: message` (e.g., `SyntaxError: Unexpected token`)
- Extract the portion before the first `:` as the error name
- This parsing will become part of the host abstraction when multi-engine support is added

## Module: Reporter

Consumes `TestResult` values and produces formatted output.

**Trait:**
```rust
trait Reporter {
    fn test_result(&mut self, result: &TestResult);
    fn finish(&mut self, summary: &RunSummary);
}
```

**Simple reporter** (`--reporter simple`, default):
- PASS: green `PASS path/to/test.js` — on TTY, overwrites previous PASS line (only failures and last pass visible)
- FAIL: red `FAIL path/to/test.js (strict)` with indented error message — persists in output
- Summary: `Ran 48231 tests | 47902 passed | 329 failed | 14.3s`

**JSON reporter** (`--reporter json`):
- Outputs JSON array to stdout, one object per test result
- `--reporter-keys` selects which fields to include

**Thread safety:**
Results arrive from Rayon threads potentially out of order. A channel (`crossbeam-channel` or `std::sync::mpsc`) funnels results to the main thread, which feeds them to the reporter sequentially. Reporters don't need to be thread-safe.

Output is in completion order by default (faster first-result feedback).

## CLI Interface

```
sonic262 [OPTIONS] <PATHS>...

Arguments:
  <PATHS>...          Test files or directories (globs supported)

Options:
      --test262-dir <DIR>       Root test262 directory (auto-detected)
      --includes-dir <DIR>      Harness includes directory (auto-detected)
      --host-path <PATH>        Path to host executable [default: node]
      --host-args <ARGS>        Comma-separated args to pass to the host
  -t, --threads <N>             Max parallel threads [default: num_cpus]
      --timeout <MS>            Per-test timeout in milliseconds [default: 10000]
  -r, --reporter <FORMAT>       Output format: simple, json [default: simple]
      --reporter-keys <KEYS>    Comma-separated keys for JSON reporter
      --features-include <F>    Only run tests with these features
      --features-exclude <F>    Skip tests with these features
      --error-for-failures      Exit with non-zero code if any test fails
  -h, --help
  -V, --version
```

The old `--root-path`, `--test-path`, `--include-path` flags are removed. Positional args with auto-detection replace them.

## Performance Expectations

Key advantages over test262-harness:
1. **True OS-level parallelism** — Rayon's work-stealing pool saturates all CPU cores, vs test262-harness's single-threaded Node.js event loop with concurrent async
2. **Harness caching** — read harness files once vs once per test (eliminates ~100k redundant file reads in a full run)
3. **Zero overhead in the harness itself** — compiled Rust binary vs Node.js runtime for the orchestration layer
4. **Work-stealing** — adapts to variable test durations automatically, no idle cores
